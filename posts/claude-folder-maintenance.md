> 当团队开始使用 Claude Code 开发后，新的技术债务也开始出现：Prompt Debt。

## 前言

最近一年，越来越多开发团队开始把 Claude Code 引入日常开发流程。刚开始接触时，大家都会做同一件事：在项目根目录创建一个 `.claude` 文件夹，然后写一些项目规范、开发约束和常用命令。

一个典型的目录结构可能是这样的：

```text
.claude/
├── CLAUDE.md
├── commands/
└── agents/
```

最开始效果通常非常明显。

Claude 知道项目使用什么技术栈，知道哪些目录不能修改，知道代码应该遵循什么规范，也知道团队有哪些特殊要求。很多原本需要反复解释的问题，只要写进 `.claude`，Claude 就能够自动遵守。

于是很多人会产生一种感觉：

> AI 开始真正理解我的项目了。

但有意思的是，随着项目持续迭代，另一个问题开始出现。很多团队的 `.claude` 最终都会变成这样：

```text
CLAUDE.md

3278 lines
```

打开之后，里面塞满了各种规则：

```markdown
禁止直接访问数据库

禁止直接修改支付状态

不要修改测试

修改接口必须确认

新增表结构必须确认

优先最小修改

优先长期可维护性

......
```

规则越来越多，文件越来越长，但 Claude 的表现却没有持续变好。有时候甚至会出现相反的情况：规则写了很多，Claude 却越来越难用。

后来我开始思考一个问题：

> `.claude` 到底是什么？以及它应该如何维护？

慢慢地我发现，大多数团队遇到的问题并不是不会写 `.claude`，而是不知道如何维护 `.claude`。

---

## 什么是 .claude

很多人第一次接触 Claude Code 时，会认为：

```text
.claude = Prompt 文件夹
```

从表面上看，这个理解没有问题。你写一些提示词，Claude 读取这些提示词，然后按照要求生成代码，看起来就是一个 Prompt 集合。

但如果仔细观察团队实际写进去的内容，会发现情况并不是这样。

例如：

```markdown
Repository 不允许跨表 Join
```

这不是 Prompt。

这是团队经验。

---

例如：

```markdown
订单状态只能由 OrderAggregate 修改
```

这也不是 Prompt。

这是业务约束。

---

再例如：

```markdown
支付状态修改必须经过 PaymentService
```

这同样不是 Prompt。

这是架构决策。

---

换句话说，代码保存的是业务逻辑，而 `.claude` 保存的是团队经验。代码告诉系统如何运行，而 `.claude` 告诉 AI 应该如何参与开发。

因此从本质上讲：

> `.claude` 更像是团队知识的机器可执行版本，而不仅仅是一组 Prompt 配置。

这也是为什么很多团队使用 Claude 一段时间之后，都会不自觉地往里面塞越来越多内容。因为他们逐渐发现：

> Claude 缺少的从来不是编程知识，而是团队知识。

它知道什么是 DDD、MVC、Repository Pattern，也知道如何编写 TypeScript、Go 或 Java 代码。但它不知道为什么你的团队规定 Repository 不能跨表 Join，不知道为什么订单状态必须通过 Aggregate 修改，也不知道为什么某个接口必须同步执行而不能异步化。

这些知识无法从公开训练数据中获得，却恰恰是项目里最重要的部分。

---

## 为什么大家都会开始写 .claude

如果回忆一下日常开发过程，你会发现很多沟通其实是重复的。带新人时，我们经常会说：

```text
这里不要直接访问数据库

这里要走 Service

这里需要考虑幂等

这里要检查缓存一致性
```

这些内容会被重复解释很多次。Claude 出现之后，这种重复沟通开始转移：以前是告诉新人，现在是告诉 Claude。

于是形成了一个非常自然的过程：

```text
口头经验
↓
文档规则
↓
CLAUDE.md
```

团队发现，只要把规则写进去，以后就不用反复解释。从这个角度来看：

> `.claude` 的本质是在降低重复沟通成本。

它承担的其实是团队知识沉淀的角色。很多开发者认为自己是在写 Prompt，实际上他们是在把长期积累的经验转换成机器能够理解的规则。

---

## 从配置文件到知识库

我觉得这是很多团队在使用 Claude Code 过程中最容易忽略的一次认知升级。刚开始使用时，我们通常把 `.claude` 当成配置文件。

例如：

```markdown
项目使用 TypeScript

使用 pnpm

禁止使用 any

统一使用 ESLint
```

这些内容当然有价值。但随着项目深入，你会发现真正影响 Claude 输出质量的，并不是这些技术栈信息，因为这些东西 Claude 本来就知道。

真正影响质量的是那些团队内部长期积累的隐性知识。

例如：

```text
为什么这里必须走消息队列

为什么订单状态不能直接更新

为什么这个接口必须同步执行

为什么这个模块禁止跨领域调用
```

这些信息既不在代码里，也不在框架文档里，但它们决定了 Claude 能否真正理解项目。当你意识到这一点时，`.claude` 的定位就会发生变化。

它不再只是一个配置目录。

它开始变成一个团队知识库。

而知识库和配置文件最大的区别在于：

> 配置只需要写进去，而知识需要持续维护。

很多团队的问题恰恰从这里开始。

---

## 为什么 .claude 最后都会失控

这里有一个特别有意思的现象：代码越写越规范，但 `.claude` 往往越写越混乱。

原因其实很简单。

代码有治理机制。

而 `.claude` 通常没有。

对于代码，我们会做：

- Code Review
- 重构
- 删除死代码
- 架构治理
- 技术债清理

但对于 CLAUDE.md，大多数团队的维护方式是这样的：

```text
Claude 犯错
↓
补一条规则
↓
继续使用
```

Claude 又犯错，再补一条规则，然后继续使用。久而久之，每个问题都通过新增规则解决，而没有人删除旧规则、整理规则或者检查规则是否仍然有效。

最终的结果就是：

```text
规则数量不断增长
```

而质量却在持续下降。

这和技术债务极其相似。

---

## Prompt Debt：一种新的技术债务

技术债务大家都很熟悉：出现 Bug，打补丁，继续开发，时间久了系统越来越复杂。

Prompt 其实也是一样。Claude 出现问题，新增规则，继续使用。时间久了：

```text
规则越来越多

上下文越来越长

冲突越来越严重
```

最终形成一种新的债务：

> Prompt Debt（Prompt 债务）

我认为这是未来所有 AI 工程团队都会遇到的问题。因为 Prompt 本质上也是一种系统，只要是系统，就会产生债务。

---

## .claude 最常见的四种腐化现象

### 规则膨胀

这是最常见的问题。最开始可能只有一句规则：

```markdown
不要直接访问数据库
```

后来变成：

```markdown
不要直接访问数据库

不要直接访问 Prisma

不要直接访问 ORM

必须通过 Repository
```

再后来：

```markdown
Repository 修改需要确认
```

规则不断叠加。很多规则其实表达的是同一个意思，但没人整理。最终 CLAUDE.md 从几十行增长到几千行。

问题在于，Claude 并不会因为规则更多而变得更聪明。相反，过长的上下文会让真正重要的规则被淹没。

---

### 规则冲突

项目在变化，规则也在变化。例如早期团队强调开发效率：

```markdown
优先最小修改
```

后来团队强调长期维护：

```markdown
优先整体重构
```

再后来又补充：

```markdown
避免大规模修改
```

这些规则单独看都没有问题，放在一起就会产生冲突。Claude 很难判断应该优先遵守哪一条。

很多团队认为规则越多越安全，但实际上冲突规则比没有规则更危险。

---

### 上下文漂移

项目已经发生变化，规则却停留在过去。例如项目已经从 React 迁移到 Next.js，但 CLAUDE.md 仍然写着：

```markdown
使用 CRA 创建页面
```

或者项目已经全面迁移 Zustand，但文档里仍然要求统一使用 Redux。

Claude 学习的是历史。

代码体现的是现实。

两者开始逐渐分离。

这就是上下文漂移。

---

### 经验失真

很多规则来源于特殊时期。例如某次线上事故之后，团队规定：

```markdown
禁止修改支付模块
```

在当时这是合理的，因为支付模块刚发生过事故，需要保持稳定。但半年后，没人记得这条规则为什么存在，规则却永久保留了下来。

Claude 仍然严格遵守。

开发者却不知道原因。

最终规则变成了一种神秘禁令。

这也是很多项目里最隐蔽的问题之一。

---

## 真正值得写进 .claude 的内容

维护半年之后，我有一个越来越明确的感受：很多团队写错了重点。

他们花大量篇幅描述：

```text
DDD

Clean Architecture

SOLID

设计模式
```

但这些东西 Claude 本来就知道。

Claude 不知道的是：

```text
为什么这里必须同步调用

为什么这里必须走 MQ

为什么这里不能跨库查询

为什么这里不能使用缓存
```

因此真正有价值的内容其实只有四类。

---

### 团队决策

例如：

```markdown
Controller 不允许直接访问 Repository
```

或者：

```markdown
订单状态只能通过领域服务修改
```

这些是团队自己的规则。Claude 无法从公开资料中获得。

---

### 历史踩坑

例如：

```markdown
库存扣减必须放事务外

原因：
曾出现长事务导致锁表问题
```

这种规则不仅告诉 Claude 应该怎么做，还告诉它为什么这么做。

---

### Review Checklist

例如：

```markdown
检查事务边界

检查缓存一致性

检查幂等性

检查异常恢复逻辑
```

这些内容天然适合作为 AI Review 的检查项。

---

### 领域规则

例如：

```markdown
订单创建后 30 分钟自动取消

支付成功后不可回退为待支付
```

这些业务规则往往比技术规范更重要。

---

## 如何工程化维护 .claude

我现在越来越倾向于一个观点：

> 把 `.claude` 当代码维护，而不是当文档维护。

代码需要重构。

规则也需要重构。

代码需要删除死代码。

规则也需要删除死规则。

代码需要 Review。

规则也需要 Review。

如果团队真的把 Claude 作为开发流程的一部分，那么 `.claude` 本身也应该纳入工程治理体系。

---

### 规则必须写原因

不要写：

```markdown
禁止修改支付模块
```

而应该写：

```markdown
禁止绕过 PaymentService 修改支付状态

原因：
支付状态同步依赖事件总线
```

没有上下文的规则最终都会变成噪音。而带有原因的规则能够长期保持可维护性。

---

### 定期清理失效规则

每隔一个季度，可以专门检查一次：

- 哪些规则已经失效
- 哪些规则已经重复
- 哪些规则已经冲突
- 哪些规则已经不再适用于当前架构

不要让规则只增不减。

---

### 优先写决策，不要写常识

不要写：

```markdown
遵循 SOLID 原则
```

写：

```markdown
Repository 禁止跨领域调用
```

不要写：

```markdown
保持代码整洁
```

写：

```markdown
新增接口必须补充 OpenAPI 定义
```

越具体的规则，Claude 的执行效果越好。越抽象的规则，价值越低。

---

## 结语

刚开始接触 Claude Code 时，我以为 `.claude` 只是一个配置目录。后来发现不是。它更像是团队经验的存储层。

代码保存业务逻辑。

文档保存知识。

而 `.claude` 保存团队共识。

但团队共识和代码一样，会腐化、会过时、会冲突，也会产生债务。

因此真正值得研究的问题从来不是：

> 如何写 `.claude`。

而是：

> 如何持续维护 `.claude`。

因为当 AI 开始参与开发流程之后，团队最终需要维护的不只是代码库，还包括一套不断演化的、面向 AI 的工程知识库。

而这，可能才是 AI 工程化真正开始的地方。
