## 项目起源

我想做的不是一个普通的作品集页面，而是一个有明确气质的个人入口：它应该像一台被接入地下网络的终端，也像一条雨夜里的新东京街道。赛博朋克美学里的霓虹、数据流、故障感、黑色空间和高饱和撞色，刚好能承载这种"技术档案库"的想象。

这个网站最终承担三个目标：

- **展示身份**：把技术、阅读、音乐和项目记录组织成一个统一的个人界面。
- **形成氛围**：让访问者一进入页面就知道这不是模板站，而是一个经过审美选择的空间。
- **方便维护**：博客、内容卡片、背景动画和部署流程都要能持续迭代，而不是一次性 Demo。

## 技术栈选择

| 模块 | 选择 | 原因 |
| --- | --- | --- |
| 前端框架 | React 18 | 组件化清晰，适合把首页、博客、音乐、书籍、联系表单拆成独立模块 |
| 构建工具 | Vite | 启动快、构建简单，适合个人站快速迭代 |
| 路由 | React Router HashRouter | GitHub Pages 上避免刷新后 404，路径形如 `#/blog` |
| 样式 | 原生 CSS | 霓虹、毛玻璃、CSS 3D、扫描线都能直接控制，不引入 UI 框架审美 |
| 博客 | Markdown + gray-matter + marked | 文章用 Markdown 写，构建时转成虚拟模块 |
| 部署 | GitHub Actions + GitHub Pages | push 后自动构建和发布 |

最重要的取舍是：**不用 UI 框架**。UI 框架会带来默认按钮、卡片、间距和字体习惯，而这个项目需要强风格控制。原生 CSS 虽然更费时间，但可以精确决定每一层光、每一条边框和每一次 hover 的质感。

## 信息架构

网站主要分成几类内容：

- 首页 Hero：作为入口，建立世界观和身份标签。
- Music / Manga / Books：承载兴趣档案，丰富个人性格。
- Blog：记录技术实践和项目复盘。
- Contact：做成加密终端式表单，延续整体世界观。

这些模块不是简单堆叠，而是被统一包装进一个"未来档案库"的概念里。比如博客不是叫 Blog，而是 `NEURAL_LOG`；分类按钮不是普通 tab，而是像终端过滤器；返回按钮使用 `<< BACK_TO_LOG` 这种命令式语言。

## 视觉规范

### 颜色系统

这个风格的核心不是"多用亮色"，而是**黑底 + 少量高纯度霓虹色**。

| Token | 色值 | 用途 |
| --- | --- | --- |
| `--bg-dark` | `#030305` | 页面主背景，接近纯黑但保留一点蓝紫感 |
| `--bg-light` | `#0d0d14` | 卡片、玻璃层、终端面板 |
| `--neon-cyan` | `#00f3ff` | 主科技色，导航、标题、边框、链接 |
| `--neon-pink` | `#ff007f` | 强调色，按钮、警示、视觉冲突 |
| `--neon-purple` | `#9d00ff` | 次级霓虹色，用于标签、阴影层 |
| `--neon-gold` | `#ffbe0b` | 少量暖色，用于书籍、档案、特殊状态 |

使用规则：

- 大面积永远是黑色或深蓝黑。
- 霓虹色只用于边框、文字、发光和状态提示。
- 同一屏最多让 2~3 种霓虹色成为主角，否则会变成杂乱的 RGB 灯效。
- 亮背景上必须加深色玻璃层，否则文字会被背景吞掉。

### 字体与文字

网站使用两类文字气质：

- `Orbitron`：用于标题、按钮、状态码、分类、导航，强调机器感。
- 中文/日文字体：用于正文，让长文本可读。

排版策略：

- 标题大写、加字距，让它像终端模块名。
- 正文不强行赛博化，保证阅读舒适。
- 功能按钮使用命令式文案，例如 `READ_MORE >>`、`RETURN_TO_LOG`。
- 装饰性文案可以像系统日志，但正文要讲人话。

### 卡片与玻璃层

博客页背景图片比较花，所以内容区域使用深色毛玻璃：

```css
.blog-section .blog-grid,
.blog-post-container {
  background: rgba(3, 3, 5, 0.64);
  backdrop-filter: blur(8px);
  border: 1px solid rgba(0, 243, 255, 0.3);
}
```

这里的关键不是 blur 越大越好，而是三者配合：

- `rgba(3, 3, 5, 0.64)` 负责压暗。
- `blur(8px)` 负责柔化背景细节。
- 青色边框负责把内容块从背景里切出来。

### 背景系统

首页和博客使用不同背景逻辑：

- 首页：绿色数据流 + CSS 3D 城市。
- 博客：`blog-intro-4.png` 和 `blog-intro-5.png` 渐变切换。

这样做是因为首页需要冲击力，博客需要可读性。背景不是统一套一个特效，而是服务页面目标。

博客背景的两图切换逻辑：

```css
.static-cyber-background {
  background: var(--blog-bg-base) center / cover no-repeat #04040a;
}

.static-cyber-background::after {
  background: var(--blog-bg-overlay) center / cover no-repeat;
  animation: blogBgCrossfade 7.2s ease-in-out infinite;
}
```

它不是简单调亮调暗，而是在两张图之间做交叉渐变，让页面像处在霓虹灯周期性变化的街景中。

## 可复用风格 Skill：Cyberpunk Personal Site Designer

如果把这个项目总结成一个可复用的风格 skill，可以这样定义：

### 目标

把普通个人网站改造成"赛博朋克技术档案库"，在保证可读性和性能的前提下，使用霓虹、终端、数据流、玻璃层和故障感建立统一视觉叙事。

### 输入

- 网站模块：Hero、Blog、Projects、Contact、Media Archive 等。
- 个人内容：技术栈、项目经历、兴趣、文章。
- 性能约束：是否允许 Canvas、CSS 3D、毛玻璃、复杂阴影。
- 可读性优先级：博客和长文本页面必须优先保证阅读。

### 输出

- 一套颜色 token。
- 背景层级方案。
- 组件视觉规范。
- 交互动效规范。
- 性能降级策略。

### 执行规则

1. **先定世界观，再定组件**：不要先画按钮，要先明确它是终端、街机、档案库还是监控屏。
2. **黑底承载，霓虹点亮**：霓虹色不能大面积铺满，否则会廉价且刺眼。
3. **动效只服务状态**：hover、加载、路由切换、背景循环都要有节奏，不要所有元素同时动。
4. **正文页面必须压背景**：长文本上方必须有玻璃层、暗色遮罩或纯色内容底。
5. **性能优先级高于装饰密度**：如果卡顿，先减少 DOM 数量、阴影、动画和 3D 层。
6. **移动端单独降级**：移动端可以保留霓虹渐变，但不要强行跑完整 3D 城市。

### 组件规范

| 组件 | 视觉规则 |
| --- | --- |
| 按钮 | 默认高亮边框；选中态填色；文字保持强对比 |
| 卡片 | 深色半透明底；细边框；hover 只轻微上浮和发光 |
| 导航 | 固定顶部；状态感强；active 有细线或发光提示 |
| 博客正文 | 玻璃层必须足够深；代码块和引用块要有不同霓虹色 |
| 背景 | 可以复杂，但不能抢正文；需要按页面类型切换 |
| 光标 | 使用自定义圆点/圆环；hover 放大，但隐藏系统鼠标 |

### 禁忌

- 不要用大面积纯绿色或纯粉色铺底。
- 不要每个元素都加大阴影。
- 不要让背景图直接贴在正文后面。
- 不要把所有字体都换成科技字体，正文会难读。
- 不要为了氛围牺牲路由、部署和内容维护。

## 值得讨论的技术点

### 1. 为什么博客用 HashRouter

GitHub Pages 默认只会返回静态文件。如果使用普通 BrowserRouter，刷新 `/blog/post-id` 时服务器找不到对应文件，容易 404。

HashRouter 把路由放在 `#` 后面：

```txt
https://liangxiuxx.github.io/Personal_Website/#/blog
```

`#` 后面的内容不会被服务器当作路径处理，所以适合 GitHub Pages。

### 2. Markdown 文章如何进入 React

项目通过 Vite 插件读取 `posts/*.md`：

- `gray-matter` 解析 frontmatter。
- `marked` 把 Markdown 转 HTML。
- 插件暴露一个虚拟模块 `virtual:posts`。
- React 组件直接 import 文章数组。

这种方式的优点是内容和代码分离，写文章时不需要手动维护 JS 数据。后续加 `updated` 字段，也只需要让插件把 frontmatter 传出来。

### 3. 为什么背景要分页面

首页可以更炫，因为用户主要是在浏览氛围和模块入口；博客页必须克制，因为用户要阅读长文本。

所以首页使用：

- 数据流 canvas
- 3D 城市
- 霓虹雾气
- 自定义光标

博客页使用：

- 两张静态背景图交叉渐变
- 深色毛玻璃内容层
- 较少动态干扰

这是一个重要原则：**同一个网站可以有统一风格，但不同页面应该有不同动效密度。**

### 4. 3D 城市为什么会卡

这个项目里的城市不是 WebGL 模型，而是大量 DOM + CSS 3D transform + 阴影 + 发光叠加。

卡顿来源主要有：

- 建筑 DOM 节点较多。
- `box-shadow`、`text-shadow`、`filter` 叠加。
- 鼠标移动和滚动会驱动相机 transform。
- 背景还有 canvas 数据流同时运行。

优化方向是：

- 建筑从更多栋减少到 8 栋。
- 远景建筑优先删除。
- 降低阴影和发光层级。
- 移动端直接使用轻量渐变背景。

这比单纯压缩图片更有效，因为真正的瓶颈在合成和重绘。

### 5. 数据流为什么要控制密度

绿色数据流很容易变成整屏绿幕。最初数据流是中间密、边缘少，后来改成每列生成，视觉更完整，但也需要降低绿色底色的透明度。

关键平衡是：

- 数据流本体可以明显。
- 绿色氛围底色要弱。
- 扫描线要轻。
- 背景不能压过前景文字。

### 6. 自定义光标的细节

自定义光标由一个 dot 和一个 ring 组成：

- dot 立即跟随鼠标。
- ring 用插值延迟跟随。
- hover 到交互元素时放大变色。
- CSS 全局隐藏系统 cursor。

这样可以保留交互反馈，同时不暴露浏览器默认鼠标形态。

### 7. GitHub Pages 自动部署

部署流程通过 GitHub Actions 完成：

```yaml
- run: npm install
- run: npm run build
- uses: actions/upload-pages-artifact@v3
- uses: actions/deploy-pages@v4
```

关键配置是 Vite 的 base：

```js
base: '/Personal_Website/'
```

否则构建后的资源路径会找不到。

## 复盘

这个项目最有价值的地方不是某一个特效，而是把视觉、内容、交互和部署串成了一套系统：

- 视觉上，有统一的霓虹语言和页面分层。
- 技术上，React 组件、Markdown 博客和 GitHub Pages 部署都能持续维护。
- 体验上，首页负责沉浸，博客负责阅读，二者没有互相抢戏。
- 性能上，通过减少 3D 城市建筑和压低背景亮度，让风格不至于变成负担。

一个风格强烈的网站最容易犯的错误，是把所有酷东西都堆到每一屏。这个项目最终学到的原则是：**风格要明确，但克制同样重要。**
