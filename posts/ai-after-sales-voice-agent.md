## 背景：为什么需要一个会打电话的AI客服

公司做智能观影设备，售后客服每天要接大量400电话——"开不了机""遥控器失灵""怎么保修"。问题是：电话客服量一大，排队、重复回答、人力成本全都上来了。

需求很直接：**用户打400电话，AI客服接听，听懂问题、照着知识库回答；搞不定的，说一声"转人工"就转给真人。**

技术栈的底子我们是有的：知识库（售后FAQ、公关话术、营销话术）已经整理成了Excel，RAG 检索的玩法在网页聊天里也验证过。真正的难点在于——**怎么把"网页上的AI"搬进"电话里"**。

## 一、先理清楚：电话里的AI，比网页难在哪

网页端AI对话，音频走浏览器 WebSocket，全是内存操作，毫秒级。

电话端不一样。传统电话音频是 **μ-law 8kHz**，要接进一个开源软交换 **FreeSWITCH**，再想尽办法把音频喂给云端的ASR、把合成的语音播回去。这里每一步都有协议、编解码、时序问题。

我一开始想偷懒，走了两条路对比：

| 方案 | 方式 | 问题 |
| --- | --- | --- |
| 方案A：阿里云智能语音交互 | 阿里云托管接听+ASR+TTS，业务方只回HTTP回调 | 半双工、体验差、控制权在别人手里 |
| 方案B：FreeSWITCH + 自建流水线 | 电话自己接，ASR/TTS借用阿里云 DashScope API | 完全可控，但要自己啃协议和时序 |

方案A适合快速验证，方案B才是能深度定制、支持打断和双工的路线。**最终选了方案B**：电话自己接（FreeSWITCH），AI能力借用阿里云 DashScope 的 API。

## 二、第一版（V4）：能跑，但慢得让人没耐心

第一版是"ESL + 文件I/O"方案：FreeSWITCH 把录音写到文件，Python 用 tail 读文件喂给ASR；TTS 合成后写WAV文件，再用 `uuid_broadcast` 播放。

能通，但体验灾难：**用户说完话要等 5~7 秒才有回应**。拆开看延迟全在浪费：

```
FreeSWITCH缓冲(文件I/O):  ~4.2秒  ← 重编译后优化到0.7秒
ASR识别:                   ~2-3秒
LLM生成:                   ~1-2秒
TTS合成:                   ~1-2秒  ← 整段合成完才播放
──────────────────────────────────
首字响应:                  ~5-7秒
```

两个最大的浪费：**双重文件I/O**（录音+播放都写磁盘）和**整段批处理**（等LLM全输出完、TTS全合成完才开口）。

## 三、第二个灵感来源：网页版已经把答案写好了

在优化电话版之前，我们其实先做了一个网页版语音Agent（浏览器麦克风+WebSocket），里面已经验证了几个让体验飙升的技巧：

1. **逐句TTS流水线**：LLM输出按句切分，每句合成完立即播放，不等整段；
2. **先出声（Filler-first）**：ASR一结束立刻播"请稍等一下"，用预生成音频掩盖等待；
3. **Barge-in 打断**：用户一开口就取消正在播的内容。

网页版首字响应能做到 ~0.5-1s。**结论很明确：把网页版的逐句流水线搬到电话线上，是提升体验的正路。**

## 四、最终版：mod_audio_stream 把音频"直传"进AI

关键突破是 FreeSWITCH 的 **mod_audio_stream** 模块——它能把通道音频以 WebSocket 实时推到外部服务，**彻底消灭文件I/O**。

```
用户拨打400 → SIP中继 → FreeSWITCH
    │
    │ 桥接程序(ESL) 下令: uuid_audio_stream start ws://.../telephony
    ▼
agent_server_websocket.py（WS主控）
    │ μ-law解码 → 流式ASR(paraformer-realtime-v2)
    │ → RAG+LLM(SSE流式) → 按句切分
    │ → 逐句TTS(CosyVoice) → 包WAV → streamAudio回传
    ▼
FreeSWITCH uuid_broadcast 播放
```

整条链路由四个进程组成：

- **FreeSWITCH**：电话交换机，负责接电话、挂住通话、播声音；
- **agent_server_ws_bridge**（ESL桥接）："总机和AI之间的接线员"，订阅电话事件、把音频推给AI、执行转人工；
- **agent_server_websocket**：AI坐席本体，ASR→RAG→TTS全在这；
- **aftersale-rag**：知识库服务，混合检索+LLM，SSE流式输出。

## 五、那些坑了一整个晚上的协议细节

这类项目90%的时间都在跟协议和时序搏斗，记录几个印象最深的：

### 坑1：mod_audio_stream 在已接通通道上"静默失败"

桥接程序在收到来电事件后，必须先 `uuid_pre_answer` 把通道退回到 PRE-ANSWER 状态，才能让 `mod_audio_stream` 挂上去；起流成功后再 `uuid_answer` 切回。**如果不按这个顺序，bgapi 返回 +OK 但实际什么都没发生**，排查起来极度迷惑。

### 坑2：uuid_broadcast 只认 .wav，不认 raw

TTS音频通过WebSocket回传时，如果发 raw PCM（`.r8`），FreeSWITCH 的 `uuid_broadcast` 不识别，内部静默失败。必须发**完整WAV（带RIFF头）**让模块落盘成 `.wav` 才能播。而且播放会截断音频开头几个字——解决办法是**前置500ms静音+后置300ms静音**。

### 坑3：DashScope TTS 传了 callback 反而没音频

`SpeechSynthesizer.call()` 如果传了 callback，音频走 `on_event` 而不是 `on_data`，导致chunk永远不生成、用户听不到回复。**不传callback，直接拿 call() 返回值。**

### 坑4：句子切分 Bug 会"丢句子"

早期实现 `out, self.buf = self.buf, ""` 把整段当一句返回，LLM 一口气输出 `S1。S2。S3。` 时只触发一次回调，后面的句子全丢了。改成按句末标点（`。！？\n`）逐句切分、剩余留buffer继续处理。

### 坑5：峰值归一化能放大，但绝不能压缩

为了让PCMA量化更清晰，对TTS音频做峰值归一化到-1dBFS是有效的；但用压缩器（ratio=3）会产生严重的"电音"失真，试过之后果断撤掉。

## 六、还有一个容易被忽略的环节：电话通道守卫

知识库是公众号文字客服的语料，里面全是"拍照发给我""扫码""公众号回复转人工"这种**纯文字指令**——电话上根本没法执行。

所以在LLM输出后加了守卫层：硬拦截"扫码/二维码/发链接"这类词，软替换"回复转人工"→"说转人工"，"拍照"类指令整句改写成"把设备情况在电话里描述给我"。

另一个合规约束是 **LLM只允许逐字复述知识库**。SYSTEM_PROMPT写死："一个字都不许改、不许加"，`temperature=0.1`。宁可回答生硬，也不能让AI乱承诺——售后场景这句话是底线。

## 七、转人工：两段式确认，防止误转

用户说"转人工""我要真人""叫你们领导"，AI先播报"正在为您转接人工客服"，然后通过 ESL 执行 `uuid_transfer` 把通话转到坐席分机（1001~1019）。用一个 `_transferring` 标志防止转接过程中ASR继续触发AI回答。

> 备注：FreeSWITCH 没配出站网关，目前只能转内部分机（坐席用软电话登录），要转手机号得先配落地线路。

## 八、结果：首字响应 1.5 秒，逐句出声

最终版的实测数据：

| 指标 | 结果 |
| --- | --- |
| 首句TTS到达延迟 | **~605ms** |
| 单句TTS合成 | 1.0s（短句）~ 5.0s（长句） |
| 整轮回复 | 3.3 ~ 5.1s |
| 首字响应（对比） | **5-7s → ~1.5s** |

关键优化就三件事：**WebSocket内存直传消灭文件I/O、LLM按句切分+逐句TTS、SSE流式不等整段。**

## 九、一些心得

1. **体验问题要先定位到架构层，而不是堆参数**。5秒延迟的根源是文件I/O和批处理，不是ASR不够快——想清楚在哪一层优化，才有一针见血的收益。
2. **先做网页版验证体验，再往电话线迁移**。逐句TTS、填充语这些技巧在网页版试错成本极低，验证有效后再搬到电话线，少走很多弯路。
3. **协议时序问题要留文档**。`pre_answer→audio_stream→answer`、WAV头、callback陷阱，这类坑不写下来，三个月后自己都会再踩一遍。
4. **AI越自由，售后越危险**。在客服场景，"只复述知识库"比"回答得聪明"更重要；给AI的自由度，永远要小于业务能承受的风险。

现在这套系统已经跑在线上：用户打400，FreeSWITCH接听，AI听懂问题、查手册、一句一句地答；答不了的，转给真人。一个"会打电话的AI客服"就这么落地了。
